# 发版手册（一页纸）

> 给维护者（项目负责人）看，不需要懂 npm、命令行或 git 标签。**每次发版只需要点一下按钮**：版本号由负责技术维护的人提前写好，你确认数字即可。

## 版本规则（本仓库约定）

| 这次改了什么 | 怎么涨 | 例子 |
| --- | --- | --- |
| 小修小补：改错别字、调样式、修 bug、优化措辞 | 最后一位 +1 | `1.0.0` → `1.0.1` |
| 加了功能，或做了较大优化（新增查询能力、新增面板、改交互） | 第一位 +1，后面归零 | `1.0.1` → `2.0.0` |

> 说明：这与 npm 社区常用的三段式（`1.1.0` 表示加功能）不完全一样，本仓库以「小修 / 大改」两档为准，够用且好记。

版本号写在 `dsh-plugins/<插件目录>/package.json` 的 `version` 字段，由技术维护在提交代码时一并改好；同一节里 `CHANGELOG.md` 会记录改了什么。

### 没有实际发版的版本怎么办

如果某个版本号写好了但**没有真正发版**（Releases 页面上没有它），下一个版本升号时要把这一版的改动**并入新版本段落**，并在正文里注明「合并自 x.y.z，未单独发布」。否则从上一个已发布版本升级的用户，会在发布说明里看不到这部分改动。

判断依据只有一个：**Releases 页面里有没有这个 tag**。没有就算没发。

## 发版：点一下按钮

1. 打开仓库的 **Actions** 页面
2. 左侧选 **DSH plugin release**，右侧点 **Run workflow**
3. 两个输入框都可以留空：
   - `plugin` 留空时默认 `threatbook-intel`
   - `version` **留空即自动读取 package.json 的版本号**（推荐）
4. 点绿色 **Run workflow**

## 自动发生了什么

- 读取并核对版本号、插件目录
- 检查 JS 语法、模块 id 与包名是否一致
- 把插件目录打成 `threatbook-intel-<版本号>.zip`
- 在 **Releases** 页面创建该版本，zip 作为附件

## 怎么确认成功

**Actions** 里最新一条是绿色勾；**Releases** 页面出现新版本和 zip 附件。

别人拿到 zip，解压后在 DSH「插件 → 添加插件」里填解压出来的目录路径即可安装。

## 失败了怎么办

点开红色那一步，把报错整段贴给我即可。常见情况只有一种：插件目录名写错（`plugin` 输入框里必须是 `dsh-plugins/` 下真实存在的文件夹名）。

## 关于 npm（可以永远不管）

只有在希望别人「填一个包名就能装」时才需要把插件发布到 npm，这是**可选**的。真要做的时候我代跑并写好说明，维护者不需要学这部分。
